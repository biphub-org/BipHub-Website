<objective>
Lay the database + application security foundation for the student role. This plan ships the single migration `00015_student_role.sql` (per ARCHITECTURE.md pre-specified scope), enables the Custom Access Token Hook in `config.toml`, adds the belt-and-suspenders role assertion to the BIP-submit Server Action, applies the migration to the local DB, and regenerates types.

Purpose: Every downstream plan (middleware routing, layout guards, the OTP flow) reads `app_metadata.role` from the JWT. Without the Custom Access Token Hook materializing the role at issuance AND the `handle_new_user` trigger materializing the `profiles` row in the same transaction as user creation, a brand-new student has a null role for up to an hour (Pitfall 1) and infinite-loops in middleware. This plan closes that hole and tightens the two RLS policies a student would otherwise exploit (FOUN-07 self-escalation, FOUN-08 BIP insert).

Output: One new migration, an enabled config hook, a hardened Server Action, applied schema, regenerated types.

**(2) handle_new_user trigger** — materializes the profile row in the SAME transaction as auth.users INSERT, so the Custom Access Token Hook can read profiles.role at first JWT issuance (D-07):
```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  insert into public.profiles (id, role)
  values (
    new.id,
    coalesce(new.raw_user_meta_data ->> 'role', 'coordinator')
  )
  on conflict (id) do nothing;
  return new;
end;
$$;

drop trigger if exists on_auth_user_created on auth.users;
create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```
NOTE: coordinator signUp passes no `data.role` → coalesce defaults to 'coordinator', preserving existing behavior. The lazy `saveProfileAction` upsert still works because the row now pre-exists (upsert on conflict id updates it). `on conflict do nothing` guarantees an existing account's role is never overwritten by a re-issued magic link (D-07 invariant).

**(3) Custom Access Token Hook** (D-06, copy verbatim from RESEARCH.md Pattern 1 / Code Examples):
```sql
create or replace function public.custom_access_token_hook(event jsonb)
returns jsonb
language plpgsql
stable
as $$
declare
  claims    jsonb;
  user_role text;
begin
  select role into user_role
    from public.profiles
   where id = (event->>'user_id')::uuid;

  claims := event->'claims';

  if jsonb_typeof(claims->'app_metadata') is null then
    claims := jsonb_set(claims, '{app_metadata}', '{}');
  end if;

  if user_role is not null then
    claims := jsonb_set(claims, '{app_metadata,role}', to_jsonb(user_role));
  end if;

  event := jsonb_set(event, '{claims}', claims);
  return event;
end;
$$;

grant usage on schema public to supabase_auth_admin;
grant execute on function public.custom_access_token_hook to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook from public, anon, authenticated;
grant select on table public.profiles to supabase_auth_admin;
```
Function MUST be `stable` (reads, does not modify). Grants scoped to `supabase_auth_admin` only.

**(4) Tighten bips_insert_coordinator** (D-12 / FOUN-08):

drop policy if exists "bips_insert_coordinator" on public.bips;
create policy "bips_insert_coordinator"
  on public.bips for insert

  with check (
    (select auth.uid()) = created_by
    and (select auth.jwt() -> 'app_metadata' ->> 'role') in ('coordinator', 'admin')

**(5) Role-stable profiles_update_own_or_admin** (D-09 / FOUN-07):
```sql
drop policy if exists "profiles_update_own_or_admin" on public.profiles;
create policy "profiles_update_own_or_admin"
  on public.profiles for update
  to authenticated
  using (
    (select auth.uid()) = id
    or (select auth.jwt() -> 'app_metadata' ->> 'role') = 'admin'
  )
  with check (
    (
      (select auth.uid()) = id
      and role = (select role from public.profiles where id = (select auth.uid()))
    )
    or (select auth.jwt() -> 'app_metadata' ->> 'role') = 'admin'
  );
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (Supabase REST API / JWT) → Postgres RLS | A student-role JWT can issue arbitrary INSERT/UPDATE against PostgREST; RLS is the enforcement layer |
| Supabase Auth engine → custom_access_token_hook | The hook runs inside the Auth engine with `supabase_auth_admin` privileges before the JWT is signed |
| client form → BIP-submit Server Action | Coordinator submit path; application-layer role check supplements RLS |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | `profiles_update_own_or_admin` UPDATE policy | mitigate | Role-stable WITH CHECK: `role = (select role from public.profiles where id = (select auth.uid()))` blocks a student writing `role='coordinator'` via REST API (FOUN-07) |
| T-05-02 | Elevation of Privilege | `bips_insert_coordinator` RLS + `submitBipAction` | mitigate | RLS WITH CHECK requires `app_metadata.role IN ('coordinator','admin')`; Server Action adds synchronous `role !== 'coordinator' && role !== 'admin'` assertion to cover the JWT-timing window (FOUN-08) |
| T-05-03 | Spoofing / null-role | `custom_access_token_hook` + `handle_new_user` | mitigate | Hook reads `profiles.role` at JWT issuance; `handle_new_user` trigger materializes the profile row in the same transaction as `auth.users` INSERT, so the first JWT carries the correct role (Pitfall 1 / D-06) |
| T-05-04 | Elevation of Privilege | `custom_access_token_hook` grants | mitigate | EXECUTE granted ONLY to `supabase_auth_admin`; revoked from `public, anon, authenticated` so no client can invoke it directly |
| T-05-05 | Tampering | `handle_new_user` re-creation | accept→mitigate | `on conflict (id) do nothing` ensures a re-issued magic link on an existing email never overwrites that account's role (D-07 one-role-per-account invariant) |
