## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /register/student RSC | Already-authenticated visitors must be bounced server-side (matcher excludes this path from middleware) |
| browser → (student) layout | Layout is the defense-in-depth guard behind the middleware D-11 matrix |
| form → signInWithOtpAction / signOutStudentAction | Client form invokes Server Actions; no client-trusted role data |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-11 | Elevation of Privilege | app/(student)/layout.tsx role guard | mitigate | Layout re-validates `getClaims()` and `role !== 'student'` → redirect by role; defense-in-depth behind middleware (D-10) |
| T-05-12 | Information Disclosure | /register/student already-auth bounce | mitigate | Page-level server-side `getClaims()` redirect (matcher excludes /register/* from middleware) so a signed-in user never sees the entry form (D-13) |
| T-05-13 | Spoofing (cross-account) | StudentMagicLinkForm email input | mitigate | Email is validated server-side in `signInWithOtpAction` (zod); the client never sets role — role is fixed server-side via options.data |
| T-05-14 | Tampering | (student) layout onboarding gate omission | accept | Intentionally NO profile-complete gate for students (D-08); students legitimately have university_id=NULL, so no coordinator-data exposure path exists |
</threat_model>
