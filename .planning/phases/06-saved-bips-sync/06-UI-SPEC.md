## Surface Inventory

### Surface 1 — Heart/Save Toggle Island on BipCard

**Location:** `components/bip/BipCard.tsx` — additive client island, card remains server-rendered.

**Layout contract:**
- The toggle is positioned absolute at `bottom-3 right-3` within the 140px gradient header (same z-layer as the existing deadline pill which is at `top-3 right-3`). This avoids text overlap in the card body.
- Island component: `SaveToggleIsland` — `'use client'`, receives `bipId: string`, `initialSaved: boolean`, `isStudent: boolean` as props.
- The parent `BipCard` RSC passes these props; data is fetched at render time by the `/bips` list RSC (one batch query: `select bip_id from saved_bips where user_id = $uid`).
- When `isStudent = false` (signed-out, coordinator, admin, or unauthenticated): render the heart button as a plain `<button>` that on click performs `router.push('/register/student')` with no optimistic toggle.
- When `isStudent = true`: optimistic toggle via `useOptimistic` + Server Action (`saveAction` / `unsaveAction`).

**Interaction states:**
```
Unsaved  → click → optimistic filled → Server Action → confirm | rollback
Saved    → click → optimistic empty  → Server Action → confirm | rollback
Signed-out / non-student → click → router.push('/register/student')
```

**Accessibility:**
- `aria-label`: "Save {BIP title}" (unsaved) / "Unsave {BIP title}" (saved)
- `aria-pressed`: `true` (saved) / `false` (unsaved)
- Keyboard: `Enter` and `Space` activate
- The button must NOT be a descendant of the `<Link>` wrapper (nested interactive elements). The card's outer element is restructured: the `<Link>` wraps only the non-interactive area, or the card is wrapped in a `<div>` with the `<Link>` as a block-level sibling. Resolution: the card outer element becomes a `<div>` with the same class list; the entire card body and header become a `<Link>` block; the `SaveToggleIsland` is a sibling of the `<Link>`, absolutely positioned over the header. The `<div>` wrapper carries `group` and hover classes.

> Rationale for bottom-of-header placement: the existing top-right deadline pill occupies `top-3 right-3`. Using `bottom-3 right-3` avoids collision and keeps the toggle visible over the gradient (white icon on dark gradient is WCAG AA compliant: blue gradient `#003399` → white icon, contrast ≥ 4.5:1).

## Interaction Contract

### Heart Toggle — State Machine

```
[Signed-out / non-student]
  └─ Click ──────────────────────────── router.push('/register/student')

[Signed-in student, unsaved]
  └─ Click ──► optimistic: fill heart ─► saveAction(bipId)
                   │                          │
                   ▼ success              ▼ error
               confirm fill            revert to empty + toast error

[Signed-in student, saved]
  └─ Click ──► optimistic: empty heart ─► unsaveAction(bipId)
                   │                          │
                   ▼ success              ▼ error
               confirm empty           revert to filled + toast error
```

- `useOptimistic` hook (React 19 built-in, available in Next.js 15).
- Server Actions: `saveAction(bipId: string)` and `unsaveAction(bipId: string)` in `lib/actions/saved-bips.ts` (new file — planner names it).
- Both actions validate via `getClaims()` before touching the database.
- `ON CONFLICT DO NOTHING` on insert means double-clicks are safe.

### Sign-in Prompt (non-student click on heart)

No modal. Immediate `router.push('/register/student')`. The registration page already explains the student account value proposition. No interstitial message needed — the destination is self-explanatory.

> Rationale: A modal asking "Sign in to save?" adds a click. The heart icon on a public page (`/bips`) when clicked by a signed-out user should route directly to sign-up, consistent with the "students only" framing of the feature (D-01).

### Unsave on `/student-dashboard/saved`

Clicking the filled heart on a card in the saved list:
1. Optimistic: card fades to 50% opacity (`opacity-50`) while the Server Action runs.
2. On success: card is removed from the list (revalidatePath or client-side filter update).
3. On error: opacity restored + toast error.

No "undo" affordance in Phase 6 (students can re-save from `/bips` or the detail page).

### Account Deletion — Student Path

Verbatim reuse of `DeleteAccountDialog` (D-04). Interaction flow:
1. Student clicks "Delete my account" button (destructive) in Account card.
2. Dialog opens (base-ui Dialog, already in use on the coordinator settings page).
3. Student reads consequences, types their email into the Input field.
4. Confirm button enables when typed email matches (case-insensitive, trimmed).
5. Student clicks "Delete account" — `deleteAccountAction` fires.
6. On success: redirect to `/?deleted=1` (existing toast island fires).
7. On error: Sonner toast with Postgres error message; dialog stays open.

## Structural Note — BipCard RSC Refactor

The current `BipCard` outer element is a `<Link>`. Nesting a `<button>` (the save toggle) inside a `<Link>` is invalid HTML (interactive inside interactive). The card must be refactored:

```
<div class="group ...hover styles...">        ← new outer; carries hover/focus classes
  <Link href="/bip/{slug}" class="block">     ← covers entire card body; block-level
    <div class="h-[140px] ...gradient...">    ← header (no interactive children)
      {country pill}
      {deadline pill}
    </div>
    <div class="p-5 ...">                     ← body
      {field chip} {title} {university} {meta}
    </div>
  </Link>
  <SaveToggleIsland                           ← sibling of Link, absolutely positioned
    class="absolute bottom-3 right-3"        ← over gradient header
    bipId={bip.id}
    bipTitle={bip.title}
    initialSaved={initialSaved}
    isStudent={isStudent}
  />
</div>
```

The `<div>` outer wrapper must replicate the hover and focus-visible styles currently on the `<Link>` (`hover:border-eu-blue hover:-translate-y-0.5 hover:shadow-md`, `focus-visible:ring-2`). The `<Link>` itself gains `focus-visible:outline-none` (focus ring moves to outer div via group-focus-visible pattern, or the Link keeps its own focus ring — planner decides the accessible focus approach).

This refactor is a visual-contract requirement, not just an implementation detail, because it changes the HTML structure of `BipCard` which is rendered on `/bips` and `/student-dashboard/saved`.
